# Ketcher 模块切换加载分析

核验日期：2026-09-11。初次分析复现了用户观察：原生接入把模块动画期间的可访问性隐藏误当成不能初始化，导致动画与画板加载串行执行；开发构建和更严格的恢复完成条件进一步放大等待。仅改为生产构建仍会留下动画结束后的加载提示。

以下初次分析保留当时的环境、测量数据和浏览器因果实验，便于与正式修复对照。后续已实施局部 loader 优化，正式实现和验收记录见文末；未重启现有服务或部署生产。

## 环境与方法

| 项目 | 实际生产 | 实际开发 | 生产构建对照 |
| --- | --- | --- | --- |
| 本机入口 | `http://127.0.0.1:9000` | `http://127.0.0.1:9001` | 临时 `http://127.0.0.1:4288` |
| 服务 | nginx 1.27.5，镜像静态文件 | Vite 7.3.6，挂载当前源码 | 当前源码 Vite production build + preview |
| 引擎 | iframe，Ketcher 3.7.0 | React，Ketcher 3.8.0 | React，Ketcher 3.8.0 |
| 版本依据 | 镜像 revision `db0fd67320bc43f2ed0e8ed9c294bbab92831670` | 当前工作区，补丁 `nexpoly-3.8.0-r3` | 补丁校验通过，输入与产物摘要见数据文件 |

使用同一个 Chrome for Testing 151.0.7922.34、1440×900 视口，开启正常动画，无网络/CPU限速，顺序执行各组。每组新建浏览器上下文，先打开画板并输入 CCO，预热后在六个画板页面进行10次所有者切换，再验证工作台→知识检索→工作台保活往返。没有提交计算任务或数据库记录；SMILES 输入使用正常标准化接口。

HTTP缓存正常启用，没有用 Playwright 路由拦截破坏缓存。每次完成后等待150ms再开始下一次导航；因此点击到开始动画的保存耗时也包含快速连续导航时可能尚未完成的快照任务。网络通过服务器本机回环访问，不代表用户电脑和公网链路。各组未随机交错，绝对毫秒数也受机器负载影响。

通过浏览器内的逐帧状态采样、模块动画事件、Worker创建和SDK渲染器记录以下不同时间：

- 编辑器内部画布已建立，有尺寸且存在SDK实例。
- CCO测试中，该页面SDK结构模型的原子数达到3，且画布有尺寸，作为结构恢复时间的代理指标。
- 当前共享文档状态为ready，加载遮罩移除。
- 模块进入idle，动画结束、交互锁解除。

旧生产没有当前原生的统一加载遮罩和同名ready状态，因此不把“iframe外壳出现”当成“内容已恢复”。原生ready也不表示所有异步化学计算API都已结束。报告中的“动画及内容均完成”取动画结束与上述内容/宿主状态完成的较晚者；没有逐帧验证像素、原子身份和键、点击可用性，也未检查旧版Hook的isEditorReady或按钮是否启用。因此它是观测指标，不应解读为两端完全等价的可交互就绪时间。

## 测量结果

下表为10次画板所有者切换的中位数；“动画后”以实际观测的动画结束为基准，不按固定1000ms推算。

| 环境 | Worker启动相对动画结束 | 结构模型恢复相对动画结束 | 动画结束后加载提示 | 点击到动画及内容均完成 |
| --- | ---: | ---: | ---: | ---: |
| 实际生产 iframe | 提前570ms | 之后246ms | 无该统一遮罩 | 1695ms |
| 实际开发 React | 之后8ms | 之后517ms | 795ms | 2640ms |
| 当前React生产构建对照 | 之后5ms | 之后177ms | 372ms | 1960ms |
| 开发React，仅调整浏览器实验中的初始化门禁 | 提前984ms | 提前594ms | 0ms | 1955ms |

实际开发加载提示尾延迟范围为724–915ms，生产构建对照为348–412ms。旧生产的SDK画布在动画结束前22–207ms已经建立，中位数提前64ms；但CCO测试中的结构模型是在结束后217–357ms达到3个原子。这解释了“生产动画结束就看到画板”的观察，同时指出编辑器界面与共享分子恢复并非同一时刻。

原生开发组10次切换均在动画结束后才创建Worker。预热后的原生切页没有再次发起SDK脚本或CSS资源请求，不能用“每次又下载了几十MB”解释这组延迟。

四组工作台→知识检索→工作台均保留原画板节点，创建Worker数为0，返回时没有动画后的画板等待。问题集中在切换画板所有者导致实例重建的路径，而非所有模块往返。

## 原因一：初始化门禁与动画交互锁耦合

两端动画参数一致：旧页淡出400ms、间隔200ms、新页淡入400ms。对应动画源码相对实际生产revision也没有差异。

`frontend/src/hooks/useModuleTransition.ts` 的 `lock()` 在切换时给业务内容容器设置 `inert`、`aria-hidden="true"` 和 `data-module-transitioning`；到新页面淡入结束后的 `finish()` 才移除。它的作用是避免不可见过渡内容接收交互。

`frontend/src/components/structure-workbench/ReactStructureEditor.tsx` 的 `visible()` 同时要求容器具有尺寸，并且任何祖先都不能有 `aria-hidden="true"`。`update()` 在这个条件不满足时直接返回，连 `import("./KetcherReactRuntime")` 都不执行。动画结束移除属性后，MutationObserver才触发SDK加载和挂载。

所以当前顺序是：

```text
生产 iframe：新页挂载 → 初始化、恢复 ─────────→
                       间隔 + 淡入动画 ────→ 动画结束

当前 React ：新页挂载 → 等待间隔 + 淡入动画 → 初始化 → 恢复 → 撤掉加载提示
```

新页在旧页淡出后才挂载，原生实现随后又放弃了名义约600ms加两帧的初始化窗口。缓存命中只能省掉模块下载，不能改变这个门禁，也不能省掉新编辑器和新Worker的建立。

当前iframe回退实现同样可以在新页面挂载时立刻加载src，其初始化只检查尺寸，没有把模块过渡的aria-hidden当成停止条件。实际生产的旧封装同样没有该限制。

## 原因二：开发运行成本确实放大等待，但不是完整解释

实际生产主程序使用压缩构建和gzip。开发侧使用源码模块、React开发运行时及Vite依赖预构建。开发源码/CSS响应为no-cache且未启用gzip；带版本的预构建依赖则可以缓存一年，不能笼统认为开发所有文件都不缓存。

实际生产Ketcher静态应用本身也很大：主JS约22.94MB，启用gzip，但其路径当前使用no-cache，不是宿主`/assets`的一年immutable策略。开发两个SDK入口静态依赖闭包约30.20MB，未计动态模块、CSS和map。这些影响首次访问；不能把磁盘体积当作预热后每次导航的实际传输量。

用当前源码生成React生产构建后，动画后的提示从中位795ms降到372ms，证明开发构建增加了明显成本；但Worker仍在动画结束后才创建，证明只打包发布不能修复时序问题。此对照使用本机preview，主要用于预热后的执行成本比较，不是生产nginx压缩链路的首屏基准。

开发每次所有者切换实际只创建1个新Worker，没有观测到StrictMode造成每次两个Worker的情况，不能把该现象直接说成“StrictMode重复加载两遍”。

## 原因三：新旧“加载完成”的定义不同

旧生产Surface直接展示iframe，没有统一的“画板加载中”遮罩。旧Hook立即检查SDK并每300ms轮询，获取初始SMILES，必要时导入共享结构；正常导入已有两次80ms提交等待。

新实现通过 `StructureEditor.tsx` 的共享状态控制遮罩。`onInit` 后，`workspace.ts` 仍要恢复KET/SMILES；原生适配器还检查导入后是否返回有效KET，再经过 `editor.ts` 的两次80ms settle，才发布ready。

这些检查是为布局恢复、避免空结果被误认为清空等正确性需求服务。当前iframe回退也使用共享恢复链，不能把全部检查成本都归因于React，或简单删除等待来取得好看的数字。新遮罩会使原先能看到编辑器外壳时仍在发生的恢复过程更显眼。

原生ready之后的250ms居中定时器不阻止遮罩消失；初始化15s和导航1.5s都是超时上限，并非固定等待。

## 原因四：保存与重建会增加整体切换时间

十次所有者切换中，两种引擎都会新建编辑器，当前没有跨六个所有者复用同一个SDK实例。共享SMILES/KET文档不等于共享SDK实例。

新导航在动画前保存双格式快照，旧版主要同步SMILES。当前 `saveSnapshot()` 会读取KET和SMILES，即使状态未标脏也会读取；SDK请求队列和已在途的快照工作可能增加等待。本组点击到退出动画开始，中位数旧生产111ms、开发479ms、React生产构建371ms。因为导航发生在短暂停留之后，不能把差值全部归因于“KET多一次导出”。

这部分解释点击后的总耗时，不能解释动画已经结束才出现的加载尾延迟；两者应分别优化。

## 因果实验及限制

在单独浏览器上下文中，仅针对原生loader容器的可见性查询，忽略带 `data-module-transitioning` 的模块容器临时aria-hidden。DOM上的aria-hidden、inert均保留；真正隐藏的保活页面、2D/3D层和零尺寸门禁保留。源码和部署没有改动。

10次切换全部在动画结束前完成宿主ready，结束后的加载提示为0。这是对“动画结束才启动”的因果验证，而非仅凭源码推测。

实验也把SDK的主线程工作移入动画期间：开发组最大长任务中位数由355ms变为290ms，但仍有长任务，点击到动画结束由1829ms变为1955ms。动画及内容均完成由2640ms变为1955ms；必须同时观察尾延迟、实际动画时长和帧表现，不能只看遮罩消失就宣布交互优化已经验收。

实验通过的原型方法拦截只存在于诊断浏览器，不应复制到产品代码。正式修复应改局部loader判定。

## 建议的修复顺序

1. **先修局部初始化门禁。** 将“容器有有效布局，允许初始化/恢复”与“允许用户事件和焦点”分开。新页面挂载后可在过渡期间准备画板；模块动画交互锁继续生效。保留真正隐藏层和零尺寸限制。不要全局删除aria-hidden检查、解除inert或用加长动画掩盖等待。
2. **补正常动画下的联合回归。** 记录新页面挂载、Worker创建、结构恢复、宿主ready、动画结束，验证初始化不再被迫等到idle。覆盖首次进入、预热互切、普通模块保活、2D/3D、快速导航及旧实例失效，并观察动画长任务和帧表现。
3. **再优化重复保存与恢复等待。** 评估无未完成写入、版本完全一致且无新编辑时复用有效快照；只有在可靠的提交/导出校验能够替代时才缩减固定settle。保留清空、无效草稿、聚合物端基及超时隔离约束。
4. **后续再做预加载和跨所有者保活。** 预加载主要改善首次进入，无法单独修复已缓存时仍存在的门禁；单实例保活需重新设计所有权与布局，收益较大但改动范围也更大。

## 此前门禁为何通过

`frontend/scripts/verify-structure-workspace.mjs` 的主画板验收使用 `reducedMotion: "reduce"`，会跳过这段动画等待；SDK兼容证明也没有这条宿主动画链。模块动画探针验证退出、间隔、进入以及交互锁，但没有要求每次画板重建在动画期间开始初始化。因此功能和生命周期检查通过，不等于已经覆盖“动画与加载并行”的性能要求。

## 局部初始化优化实现

本期产品源码只调整 `ReactStructureEditor.tsx` 并提取懒加载函数 `loadKetcherRuntime.ts`，新增真实共享文档管理器配合模拟 SDK 的 loader 集成测试。

- 初始化和恢复检查 DOM 连接、有效尺寸及隐藏祖先。只有实际最近的模块内容容器，在 `data-module-transitioning="true"` 且阶段为 `blank/entering` 时，允许绕过它的 `aria-hidden`；嵌套隐藏、2D/3D 隐藏层、保活页面和退出阶段继续阻止新初始化。
- 交互与居中继续检查 `hidden/aria-hidden/inert`。只有共享状态 ready 且解锁后，才启动原有 250ms 防抖居中；重新锁定、隐藏和会话销毁都会取消任务。加载或锁定时先检查状态，避免无必要的布局读取。
- 动态加载和文档恢复各有会话内的单次启动保护。资源加载途中隐藏仍可完成加载，文档恢复前重新检查条件。初始真正隐藏时不启动 15 秒加载计时。保留旧回调失效和同引擎重试。
- SDK 组件以当前 session 的稳定 props 建立 `memo` 边界，避免宿主阶段和共享状态变化重复渲染整个 SDK；SDK 自身状态更新及页面所有者切换的实例重建保持正常。
- 观察器增加模块阶段、过渡标记和 `inert`。没有修改宿主 DOM 原型、SDK 补丁、依赖、动画参数、共享文档格式、ready 定义或两次 80ms 提交等待。

定位过程中试验过两帧后挂载、低优先级挂载、额外挂载间隔和 CSS containment。它们没有稳定满足开发性能门禁，最终实现未保留这些试验。

## 正式验证方法与功能结果

基线是在编辑前保存的完整前端源码副本及 React 生产构建。最终逐文件比较确认，除 loader 和新增 helper/test 外，其余前端产品源码与基线一致。动画 Hook、共享文档管理器、锁文件和 SDK 补丁清单的 SHA256 保持一致。

性能对照使用同机 Chrome 151.0.7922.34、1440×900、CCO、正常动画、正常浏览器 HTTP 缓存，无 CPU/网络限速、无路由拦截。开发基线/优化服务为 5287/5288，原生生产构建基线/优化为 4287/4288。全部服务都是独立临时实例；实际生产 9000 保持只读。

每组使用新浏览器上下文，记录首次空文档加载；输入 CCO 后预先固定走一轮六个所有者，预热 KET 恢复路径，再记录十次所有者切换及普通模块保活往返。六次预热全部单独保留，不根据耗时剔除样本。开发与生产各三轮，第二轮交换基线/优化执行顺序。各组顺序运行，性能测量时不同时运行构建、测试或其他浏览器探针。

逐帧记录阶段、SDK、Worker、原子数、共享 ready、按钮状态和帧间隔；通过 PerformanceObserver 记录长任务。几何与命中检查在状态变化、解锁以及等待首次有效命中时执行，避免每一帧都强制布局；同时记录探针自身执行耗时。结束条件仍要求真实原子位于可见区域、可以命中且业务按钮可用，计时窗口外再导出实际 SMILES 校验 CCO。功能探针另外执行真实鼠标选择、拖动、键盘和弹窗操作。

**开发模式仅在合并口径下接近门槛通过，不能宣称每轮稳定达标。** 合并动画时长增量 199.3ms 距 200ms 上限只有 0.7ms；逐轮情况如下：

| 模式 | 第 1 轮增量 | 第 2 轮增量 | 第 3 轮增量 |
| --- | ---: | ---: | ---: |
| 开发 React | **237.0ms** | 133.2ms | **238.1ms** |
| 生产构建 React | 32.7ms | 105.0ms | 21.4ms |

开发有两轮超过单轮 200ms，因此这里的“门禁通过”严格指上述合并样本规则。当前 SDK 初始化仍包含较长的主线程同步渲染，运行负载变化可能使开发结果越过上限；没有通过重复选择某一轮的有利结果替换失败记录。若发布要求是“每一轮都不超过 200ms”或更稳定的动画流畅度，本次结果不足以满足该更严格标准。

提前初始化也把工作移入过渡期间：退出/进入阶段的帧间隔 P95，开发由 36.0ms 增至 72.4ms，生产构建由 31.0ms 增至 39.1ms。开发最大帧间隔从 170.1ms 降至 108.7ms，但 P95 变大，不能据此宣传动画更流畅。长任务 P95 分别为开发 334→313ms、生产构建 95→94ms；主线程长任务仍然存在。探针自身耗时 P95 为开发基线/优化 0.2/0.4ms、生产构建 0.2/0.5ms。

首次空文档直接进入、全新浏览器上下文的就绪时间范围：开发基线 3.73–4.41s，优化 3.22–4.45s；生产构建基线 4.87–5.53s，优化 4.93–5.31s。本期没有优化大型 SDK 的冷加载体积，不据这组本机 preview 数据声称首次访问变快。由普通模块首次进入画板时，功能探针确认资源请求在 `blank/entering` 启动；冷资源仍可能在动画结束后才完成。

构建仍交付相同 SDK/补丁和 iframe 回退。最终原生 SDK 主分块约 23.20MB（未压缩）；没有加载体积收益的承诺。连续重挂载并强制 GC 后，开发堆从约 121.17MB 到 121.58MB，生产构建从 89.26MB 到 89.65MB，旧实例 WeakRef 均释放，DOM 与监听器初末一致。这些数值反映本机样本，不是跨设备内存上限。
