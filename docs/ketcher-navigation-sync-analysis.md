**Ketcher 连续切换模块时的同步提示：原因与解决方案**

复核日期：2026-09-11。以下首先保留源码分析与修复前浏览器复现，文末记录用户要求修复后的实现及验收。复现按左侧模块连续切换进行；生产环境未部署。

这属于导航保存与编辑器生命周期衔接的问题。已复现“没有新增修改，却提示最新修改未能同步”，不是原生组件必然出现的正常现象。截图自身不能证明发生了内容丢失，也不能证明是复杂聚合物导致解析超时。

**浏览器证据**

使用当前开发环境 `http://127.0.0.1:9001`、原生 Ketcher 3.8.0、1440×900、正常动画、CCO 文档。业务 API 使用浏览器本地响应，不提交任务或记录。诊断只在独立浏览器上下文记录工作区方法调用、状态和导航阶段。

| 操作 | 实际结果 | 解释 |
| --- | --- | --- |
| 同一目标模块双击，间隔 80ms | 无提示，最终结构为 CCO | 现有同目标去重正常，不能笼统归因于“没有防抖”。 |
| 两个不同目标在第一次路由提交前连续点击 | 无提示，最终进入最新目标，结构保留 | 尚未提交的导航可以合并目标。 |
| 先切到相似性探索，在它刚进入 `blank/loading` 时再切回均聚物预测 | 出现截图同文案，最终结构仍为 CCO | 保存约 0.4ms 即返回 `failed: 结构编辑器尚未就绪。`，不是等满 1.5 秒。 |
| 发起切页后立即点回原模块，并将 KET 导出结果人为延后 1900ms | 页面已处于 `idle`，约 1.5 秒后仍弹提示并重建当前画板 | 取消导航没有取消 App 内的超时恢复。此例明确使用故障注入验证边界。 |

第三例用 DOM 观察精确触发第二次侧栏点击，没有人为延迟 SDK。触发失败时，记录为 `dirty=false`、`mutationDepth=0`、草稿与共享 SMILES 一致、文档版本与最后有效快照版本一致。因而这次“最新修改未能同步”属于误报。

四例最终导出的 SMILES 都是 CCO，最终诊断没有未处理页面异常。它们不代表截图中完整聚合物的性能测量，也不替代修复后的全量回归。完整调用轨迹、浏览器版本及源码摘要见 [验证数据](/data/lzq/gith/nexpoly-dev/docs/verification/ketcher-navigation-sync-analysis.json)。

**原因一：将初始化状态当成保存失败**

连续切换的关键路径是：

1. A 页保存成功，开始切换到 B 页。
2. B 页已成为当前模块，新的画板仍在初始化或恢复；共享文档已经保存完整。
3. 用户此时选择 C 页，App 对 B 页再次执行离页保存。
4. `saveSnapshot()` 只允许读取 `ready` 编辑器；`loading` 会立即返回失败。
5. App 把所有非 `saved` 结果交给恢复逻辑，销毁实例、增加 `mountKey`、恢复最后快照并显示同一条警告。

对应代码为 [未就绪判定](/data/lzq/gith/nexpoly-dev/frontend/src/structure/workspace.ts:299)、[App 的统一失败处理](/data/lzq/gith/nexpoly-dev/frontend/src/App.tsx:400)、[恢复与提示](/data/lzq/gith/nexpoly-dev/frontend/src/structure/workspace.ts:354)。

这里缺少的语义是：“刚挂载的编辑器只是共享文档的恢复目标，目前没有需要从它抢救的新修改。”正常更换页面本来就会清理旧实例，错误恢复又触发了一次挂载更新，增加了无必要的重建。

重复点击的结果取决于第二次点击发生在路由提交前还是提交后。同一目标的去重已经存在；新目标在 B 页提交后到来，会开始一次针对 B 页的新保存。这解释了为何普通连续点击可能正常，落在特定时间窗口却会弹提示。

**原因二：导航取消只取消了路由等待，未取消恢复副作用**

[模块过渡取消逻辑](/data/lzq/gith/nexpoly-dev/frontend/src/hooks/useModuleTransition.ts:297) 会调用 `wait.cancel()`；[通用 guard](/data/lzq/gith/nexpoly-dev/frontend/src/hooks/useGuardedNavigation.ts:7) 仅将等待结果设为不允许导航，没有把取消信号传给 App 的保存事务。

App 内部的保存 Promise 和 1.5 秒定时器因此继续存在。`finish()` 只检查自身是否已经结束，没有检查导航是否已取消、是否仍属于原编辑器。导出较慢时，即使用户决定留在原页，它仍调用 `recoverForNavigation()`。

受控复现中，恢复发生时模块已经是 `idle`，且内容未修改；仍然出现提示并重建同一页面的画板。如果用户在取消后继续编辑，这个无效导航的恢复就有覆盖新增画板修改的风险。此次没有把该风险描述为已发生的数据丢失。

此外，通用 guard 和 App 各自维护一个 1500ms 定时器，路由放行与旧会话失效的顺序依赖两个回调的调度。修复应收敛为同一导航事务拥有截止时间和取消处理；本次没有单独证明该双定时器已造成新实例被错误销毁。

**增加等待的因素：快照重复读取**

当前 `saveSnapshot()` 即使 `dirty=false` 也导出 KET 和 SMILES；它停止尚未触发的防抖定时器，但不会合并已经进行的快照读取。自动保存与离页保存可能同时针对同一版本读取，而底层 Worker 请求实际串行执行。

本次轨迹可见自动保存尚未完成时离页保存再次进入。复杂结构和主线程负载可能放大等待，但截图中的分子没有在本次原样测量，不能将这点认定为本次弹窗的直接原因。第一条已复现路径无需慢 Worker 也会触发。

最近的加载优化调整了原生编辑器的初始化与交互时机，`workspace.ts`、导航保存和取消逻辑未因此修改。既有快速切换验收验证了最终目标、内容和单实例，但缺少“加载中未修改不得误报”和“取消后超时不得恢复”的断言。这是需要补齐的交叉时序覆盖。

**建议实施顺序**

1. **先修复加载期间的导航判定。** 在共享文档管理器内部增加离页决策，区分已保存且未变的文档、未提交的画板修改、文本草稿与初始化。只有确认当前有效文档已由快照完整覆盖、没有未完成写入和新增画板修改时，才直接沿用文档离开。不能将所有 `loading` 一律判成功，也不能仅凭 SMILES 相同忽略布局变化。无效草稿独立保留，不当作画板保存失败；初始化暂空不能提交为空文档。外部已验证 SMILES 与旧 KET 的失效关系继续遵守现有规则。

2. **让取消和超时属于同一个导航事务。** 为离页事务保存取消信号、事务标识、来源编辑器身份与截止时间。取消后清除该导航的计时器，使它的迟到结果不再触发通知、回滚或重挂载。真正超时时，只处理仍有效且仍属于原会话的任务，先使旧任务失效，再继续切页。保持 1.5 秒上限、同目标去重和最新目标优先。正常页面卸载承担实例清理；取消后留在当前页，不因过期导航销毁当前编辑器。

3. **合并同版本快照读取。** 以编辑器身份、会话及文档版本识别正在进行的捕获，使自动保存与导航共用同一次结果。已有成功快照覆盖当前版本、且无待提交修改时直接返回。读取期间出现新编辑，仍丢弃旧结果并捕获新版本，保留布局变化、明确清空和聚合物端基保护。单个导航取消只退出其等待，不应连带取消其他消费者需要的自动保存。

4. **按真实结果显示提示并补充诊断。** 无变化离开不显示同步失败；取消导航不显示恢复提示；确有未保存画板修改且失败或超时，继续显示恢复提示。只有草稿待处理时，使用准确的草稿提示，不声称画板丢失修改。开发诊断记录阶段、原因、耗时、版本和会话标识即可，无需记录完整化学结构。

建议主要改动 `workspace.ts`、App 保存桥接、`useModuleTransition.ts` / `useGuardedNavigation.ts` 的取消及截止协调；必要时将 `useTgStructureCanvas.ts` 的草稿提交等待接入同一事务。业务画板接口、SDK 补丁、动画时长、React/iframe 构建选择继续沿用。重复快照合并可在前两项修复后单独验证，避免将性能优化与正确性修复混为一个不可拆分的大改动。

**修复实施与最终验收（2026-09-11）**

已完成以下实现，生产环境未部署：

- `saveForNavigation()` 先确认有效快照是否覆盖当前文档及版本，并检查是否存在进行中的写入。已保存的文档在新编辑器加载期间可以直接离开；未保存的布局修改仍进入完整 KET/SMILES 捕获。初始空文档不伪造 SDK 快照，首次自动保存仍建立完整空 KET。
- `waitForGuard()` 持有唯一的 1500ms 导航定时器。`AbortError` 取消该导航的等待；`TimeoutError` 在放行路由前触发恢复。新增结构导航桥接按原会话身份检查回调；App 删除第二个定时器及会在取消后残留的 Promise 缓存。取消不影响保留页面的编辑和其他消费者的自动保存。
- 自动保存和离页保存共享同一会话、同一版本正在进行的捕获。后续编辑仍通过版本检查排除迟到结果。“生成SMILES”等显式读取继续从 SDK 导出。
- 加载中的文本草稿留在 App，由目标页恢复后继续校验；仅草稿待同步时使用准确提示，草稿接受后清除该提示。外部已经验证的 SMILES 成为有效共享文档，避免加载时导航恢复过期 KET。恢复快照时同步推进其版本，避免紧接着再次切页又被当作未保存。

SDK 四包、补丁、锁文件、原生 loader、动画参数及 ready 判定保持不变；`StructureEditorHandle`、共享 Context 和同步结果状态保持兼容。画板页面的 `syncBeforeLeave` 增加可选 AbortSignal。
