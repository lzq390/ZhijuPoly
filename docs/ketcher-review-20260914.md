## 结论与已修复问题

当前范围包括原生 Ketcher 3.8/r3 集成、iframe 回退、共享文档与导航所有权、SDK 生命周期与 Worker 隔离、路由按需加载、启动预加载和开发响应压缩。完成修复和以下复验后，未发现尚未解决的提交阻断项。

1. **CSS 失败重试存在两处遗漏。** Vite 的 preload helper 等待全部样式，但只抛出首个错误，内部 `seen` 又会跳过其余失败资源；实际 Chromium 中，失败链接也可能仍有非空 `sheet`，不能据此认为加载成功。`retryModuleImport.ts` 现在收集本次真实样式错误，并在重试时等待全部恢复；已捕获失败的原链接必须重试，共享重试、属性与 nonce 保留，已成功替换的样式不再替换。新增五项回归覆盖多份同时失败、并发共享、重复失败、失败后的非空 sheet 及已恢复链接复用；其中多份失败测试使用本地实际 Vite helper。
2. **Docker 校验仍假定业务代码位于 HTML 入口包。** 路由拆包后，该检查会误报，还可能从不相关资源误认配置。新增 manifest 图校验器，根据业务消费者的静态依赖闭包核对 workspace URL、资源存在性及 nginx 可访问性；原有文件权限和引擎资源检查保留。14 项 fixture 覆盖缺失资源、配置落错分块等情况。
3. **浏览器探针混入环境假设。** AI 初始化脚本只在应用顶层同源页面设置 localStorage，避免被阻止的外部 iframe 错误文档触发访问异常；仍保留所有产品 `pageerror` 断言。刷新/HMR 探针使用明确页面标题，兼容候选的原页面结构，并使用固定 `CCO` API fixture，不依赖本机后端。初次失败记录完整保留。
4. **分析文档对 SDK 执行时机描述过度。** 旧独立 root 原型的 HTML `modulepreload` 本身不执行模块，但 `main.tsx` 触发的动态 import 已开始 SDK 求值。尚未提前的是挂载时创建的服务/Worker。已修正剩余性能分析，避免把已有模块执行误当作新的优化空间。

## 边界与后续

`npm audit` 报告 15 个依赖节点：9 个是旧 lock 同版本的开发依赖，6 个属于 SDK 依赖链。Draft.js 实际使用受影响的 Immutable，旧 iframe 包也含相同不安全的 `toObject` 实现；本轮未建立新增的有害产品利用链，但不能称为无漏洞。兼容升级与导入数据限制需单独处理，不能盲目 `audit fix` 升级 Ketcher 而破坏 r3 补丁。

模块入口/CSS 重试不保证所有传递依赖失败都能在原文档恢复，详见[已记录的浏览器限制](ketcher-refresh-optimization.md)。本轮没有移除 160ms 文档提交等待，也没有引入预热 Worker 或修改 Macro 初始化。

此前性能测量及原型数据保留各自日期和实验范围。本轮候选验证是功能与交付 review，不能代替相同环境下的新性能测量，也不表示已达到“快于9000”的目标。9000 未更新；本轮没有重建或重启实际9001，根工作区修复可能通过现有源码绑定触发其 HMR。
