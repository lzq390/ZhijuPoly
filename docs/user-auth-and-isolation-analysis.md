# NexPoly 用户登录、权限与数据隔离分析

分析日期：2026-09-10。代码基线：db0fd67。

本文基于当前仓库的前端、API、PostgreSQL 迁移、仓储、计算 Worker 和部署文档做静态分析。未连接运行服务、读取实际业务数据或密钥；功能实际启用情况、生产外围认证、TLS、数据库运行角色仍需在实施阶段核验。本文是建设方案，不表示用户系统已经实现。

状态：设计草案，尚未实现。本文给出个人／团队工作空间的完整设计方向；如果首期只需要两个同等权限的普通账号，收窄范围的方案见[普通用户 MVP 与任务协调](ordinary-user-mvp-isolation-and-scheduling.md)。MVP 使用个人归属字段并暂缓空间／成员模型；本文的长期结构不是与 MVP 同时执行的迁移清单。所有现状判断对应上述历史基线，实施前需按届时源码重新核验。

## 1. 结论与建议范围

当前 NexPoly 已经是包含科研资料检索、结构处理、AI 设计、实验数据和异步计算的共享工作台。用户隔离需要贯通“身份 → 权限 → 资源归属 → 异步任务 → 文件与缓存 → 独立 Agent 服务”，登录页面只是其中一部分。

建议以内部研发团队为第一阶段假设：邀请制账号、平台共享资料只读、每人默认个人工作空间、私有成果默认不共享，团队协作通过明确的空间成员和共享权限开放。需要支持外部企业时，再决定是否增加组织层或独立部署。

推荐技术路线是保留 React/FastAPI/PostgreSQL 和现有计算运行时，增加集中会话管理、权限上下文、资源归属、仓储过滤及数据库防线。共享只读科学数据与模型资产不必按用户复制。普通科研操作先采用逻辑隔离；具备文件和命令工具的 Agent 要另外落实执行环境边界。

第一版不能遗漏：现有业务 API、历史列表与统计、任务查询/取消/删除、轨迹和产物下载、浏览器残留、OpenScience 直接入口、管理员能力和历史数据归属。公开注册、复杂组织层级、计费系统、全量 Demo 产品化可以后续建设。

## 4. 先确定隔离语义

“用户隔离”至少包含五个独立目标：

1. 身份：账号是谁、是否启用、会话是否有效。
2. 操作：能否查看、提交计算、导出、取消、删除、管理成员或运行运维操作。
3. 数据：可以接触哪些资料、实验记录、候选结构、任务、对话和文件。
4. 资源：可占用多少 GPU、CPU、外部模型额度、队列和存储。
5. 执行：Agent 或其他可执行代码能力能读写哪些目录、调用哪些服务。

建议采用下列数据分类：

| 数据类别 | 建议归属与默认规则 |
|---|---|
| 平台共享科学资料 | core、knowledge、pi、静态 dft、experimental 导入数据及模型资产；经确认可共享后，供有权限的登录用户只读。“平台共享”不等于匿名互联网公开 |
| 个人研究成果 | 输入结构、候选、私人检索历史、对话、草稿和计算产物；默认个人空间可见 |
| 团队研究数据 | 主动写入或分享至团队空间的实验/任务/成果；按成员、项目与操作权限访问 |
| 平台管理数据 | 用户、成员、配额、供应商配置、审计、全局运行状态；按管理职责授权 |
| 示例与历史遗留 | 示例用明确标识；旧真实记录放受限归档空间，归属不明不能当公开数据 |

现有 lab.test_projects 主要表示测试项目类别，页面中的 experimentProject 示例包括 Tg；operator 为可编辑的操作员字符串。它们不能代替租户/科研项目关系或登录用户。实验 Demo 的人员数组同样不是账号系统。

若目标只是每个人互不相见，可第一期只开放个人工作空间。保留 workspace 抽象有利于以后团队协作，但无需现在同时建设复杂 organization/department/project 多层体系。

同一团队空间是否仍允许个人私有记录需要明确。若允许，workspace_id 只能解决空间之间的隔离，还需要 owner_user_id、visibility 或资源授权关系；不能把“是空间成员”直接等同于“能读空间内所有私人内容”。

## 5. 账号、登录与会话系统

第一版账号功能建议包括邀请/开通、登录、退出、当前用户、修改密码或 SSO 账户管理、忘记密码/受控重置、账号启用与禁用、成员管理、会话撤销、基本审计。邀请和重置链接应单次使用、有有效期，首次管理员通过受控初始化产生。建议管理员启用 MFA，敏感权限变更与账户恢复要求再次验证身份。

如果组织已有身份提供方，优先接入 OIDC 单点登录；没有时可先做邀请制本地账号。使用 SSO 仍需本地用户 ID、有效成员关系和权限模型，并以身份提供方 issuer + subject 绑定账号，不能仅凭显示名或未验证邮箱合并身份。账号限速、恢复和敏感操作再认证可参照 [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

当前 React 和 API 经同一入口提供服务，建议用服务端保存的随机会话令牌，浏览器使用 HttpOnly、Secure、明确 SameSite 的 Cookie；服务端保存令牌摘要、用户、创建/到期/撤销信息。已有 PostgreSQL 可承担第一期会话存储，后续根据实测负载决定是否引入 Redis。登录与提权后轮换会话；本地密码采用成熟 Argon2id 实现。依据：[会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

需要明确会话空闲和绝对超时、多设备策略、修改密码后撤销旧会话、禁用账号立即拒绝后续请求、成员移除后撤销空间访问。长期 JWT 若没有撤销或权限版本机制，会让“后台禁用”与“实际还能访问”出现时间差。第一期不必为了登录强行使用 JWT。

采用 Cookie 后必须补充写请求的 CSRF token/可信来源校验，保留现有浏览器跨站防护；登录、退出和管理员接口也要覆盖。GET 应保持只读，当前分析刷新应拆为受限 POST。SameSite 不是完整 CSRF 防护，参照 [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

登录凭证不放 LocalStorage/sessionStorage，不通过普通 URL、日志或 iframe 消息广播。HttpOnly 不能阻止恶意同源脚本借用户身份操作，因此还需正确处理文献/模型富文本、SVG、上传内容和 CSP 等浏览器边界。

## 6. 权限模型与后端强制执行

建议将平台角色与空间角色分开：平台运维负责运行环境；账号管理员负责开通禁用；空间负责人管理成员和空间设置；成员提交和管理获授权成果；只读成员仅查看获授权资源。小团队可以由同一个人兼任多个角色，但权限定义不能混在一起。

| 操作 | 普通成员 | 空间负责人 | 平台管理/运维 |
|---|---|---|---|
| 读平台共享资料 | 按模块权限 | 按模块权限 | 按模块权限 |
| 创建实验/计算/检索 | 在有写入权的空间内且额度足够 | 同左 | 不因运维身份自动获得科研写权限 |
| 查看/下载私人结果 | 本人或明确获授权 | 按私有/共享政策，不能默认为全可读 | 默认不获得全部私人数据权限 |
| 取消/删除任务 | 本人且动作被允许 | 明确获授的空间管理范围 | 应急路径单独授权并审计 |
| 管理成员 | 否 | 仅所属空间 | 账号与平台职责范围内 |
| 配置共享模型密钥/刷新全局快照/GPU 恢复 | 否 | 默认否 | 对应管理权限 |

统一建立服务端 AccessContext，包含 user_id、已校验的 workspace_id、有效成员关系、权限与请求 ID。客户端的工作空间参数只能作为选择条件，后端必须校验当前用户是否仍有该空间权限。模块可用性还应满足部署开关和运行时状态；授予 DFT 权限不能覆盖生产 hard-off。

实现顺序为“验证会话 → 校验空间成员及模块/操作权限 → 带归属条件访问资源”。仓储接口必须显式接收作用域；缺少上下文默认拒绝。所有列表、total/count、聚合、筛选选项、详情、更新、删除、清空、取消和下载都使用相同规则。OWASP 强调每次请求校验权限和默认拒绝，见 [Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

错误语义也要一致：未登录为 401；无操作权限为 403；不属于调用者可见范围的资源可统一返回 404，避免暴露存在性。现有 DFT 自定义错误 envelope 应支持这些情况，不破坏前端错误解析。任务已过期的 410 语义要与未授权情形区分，并避免暴露他人任务是否曾存在。

建议维护“路由 → 身份类型 → 操作权限 → 资源作用域”清单，使新增接口必须明确分类。公开例外仅保留必要登录/回调和最小健康检查；Worker、发布控制和运维接口使用独立服务身份及网络规则，不应简单加入“所有登录用户可访问”。

## 7. 数据模型、约束与 PostgreSQL 防线

可按以下最小数据模型设计，名称是建议而非现有实现：

| 新实体 | 关键内容 |
|---|---|
| users | 稳定 ID、规范化登录名/邮箱、启用状态、时间；本地密码摘要或外部身份关联 |
| external_identities | issuer、subject、user_id；采用 SSO 时需要 |
| sessions | 令牌摘要、user_id、创建/最后活动/到期/撤销时间、权限版本 |
| workspaces | 名称、个人/团队类型、状态与生命周期 |
| workspace_memberships | workspace_id + user_id 唯一、角色、成员状态 |
| invitations / reset_tokens | 单次令牌摘要、用途、邀请范围、有效期和消费状态 |
| audit_events | 操作者、空间、动作、资源、结果、时间、request_id |
| quota_policies / usage_records | 限额、预留、实际消耗、释放和归属；按任务一致性需求实现 |

业务主记录增加 workspace_id、created_by，按需求增加 owner_user_id、visibility、updated_by；created_by 作为不可随意改写的审计信息，转移所有权不能重写创建历史。项目级权限确有需求时再引入独立科研项目和成员关系。

优先改造 online_knowledge.history/jobs、lab.sample_measurements、md.monomer_md_jobs、monomer_dft.jobs 及三类内存任务。lab.test_projects 先判断是平台共享测试字典还是允许空间自定义；不能机械给所有表增加相同 owner 规则。

子表/产物可通过父任务继承归属，或存冗余 workspace_id 并用复合外键保证一致。无论采用哪种方案，都要阻止把 A 空间的子记录挂到 B 空间任务/项目下。

必须同步调整以下语义：

- 样品编号唯一性：从全局 sample_id 改为空间内唯一；若业务要求项目内唯一，再加 project_id。
- 在线历史：至少按 workspace/user + material + mode 去重；若要保留每次检索，应改为独立历史记录，查询复用缓存另建。
- DFT 幂等：按 workspace + actor + operation + idempotency_key 定义唯一范围，保留请求 hash 校验；授权在幂等命中返回之前执行。
- 查询和分页索引：根据常用条件建立 workspace_id 与 created_at/status/project 的联合索引，并验证查询计划。
- 批量导入/更新、ON CONFLICT、删除、子表关联和清空操作同步调整，不能只改 SELECT。

在线 CSV 导出当前是把请求体中的数据转成 CSV，尚不是从数据库按资源 ID 自动导出；它仍需登录与限制。未来增加保存结果、批量导出或文件库时，必须先按归属查询。已发送给浏览器或已下载的文件无法靠后续撤权追回。

当前使用 psycopg/手写 SQL，无现成 ORM 租户过滤器；[postgres_connection](../backend/app/postgres_database.py) 也只接收 DSN。建议以受限仓储访问为第一层，在私有业务表加入 PostgreSQL RLS 作为第二层，并同步设计不同数据库连接路径。

实验数据实际走 lab_data_postgres_dsn，配置可以与 app_postgres_dsn 不同，见 [实验数据连接](../backend/app/routers/lab_data.py)。实施前需确认这些 DSN 是否指向同库；不能假设新增 users/workspaces 后所有业务库都能直接建立外键。若继续分库，应明确身份引用的校验/同步方式、各库运行角色与事务上下文，不能只保护主库连接。

RLS 实施需要：普通 API 使用非超级用户、非 BYPASSRLS 的最小权限角色；处理表所有者的绕过行为；按实际需要启用 FORCE ROW LEVEL SECURITY；覆盖 USING 与写入检查；身份在同一事务内设置并在结束时释放；独立处理 Worker、迁移和审计角色。RLS 不约束超级用户/BYPASSRLS，TRUNCATE 也不受行策略约束，因此普通角色不应有整表管理能力。参照 [PostgreSQL 16 行安全策略](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)。

事务上下文必须由后端验证身份后建立，每笔事务使用 SET LOCAL 或事务局部 set_config。当前没有连接池，未来引入池化仍须测试连接复用；不能让上一请求的空间状态进入下一请求。此处与缓存、异步上下文的分类原则可参照 [OWASP 多租户安全](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)。

工作空间级 RLS 并不自动解决同空间个人私有记录的授权，应按选定政策补 owner/visibility 检查。RLS 也不能隔离拥有宿主机或数据库超级权限的管理员；若要求彼此不信任的外部机构隔离，还需评估独立数据库凭据、文件存储、备份和运行环境。

## 8. 异步任务、Worker、资源公平性与文件

每个作业创建时固定“空间、提交者、输入、资源策略、版本”，之后在排队、执行、重试、结果回写、下载和清理中保持一致。不要将浏览器会话令牌写进持久化作业或用作 Worker 凭证。

Worker 使用服务身份；attempt_token 用于执行尝试关联，fencing_token 用于租约有效性，它们都不等于用户身份。API 必须在向 Worker 发送取消/下载/删除请求前完成授权。后台回写应核对 job/attempt/worker 关系；后台清理和 reconciler 的跨空间工作需要明确系统职责与审计。

产品默认建议：用户退出后已提交任务继续；退出终止浏览器轮询和显示。用户被禁用或移出空间后，禁止新提交及继续读取；尚未运行/正在运行的任务按既定策略取消、继续或由空间负责人接管。归属不可因退出或禁用变为空。

条件生成、PolyTAO、Tg 逆向设计可以先在现有内存记录补充归属，完成短期隔离。若承诺“我的任务跨设备可恢复、重启后可追踪、多副本可服务”，则必须进一步持久化元数据/结果，明确中断恢复和失败状态。在线知识任务虽已入库，但由 FastAPI BackgroundTasks 执行，也要补重启后失联任务识别与重试规则。不要恢复已退役的 PolyTAO 旧表来绕过现有迁移治理。

用户隔离还应限制资源占用：每用户/空间提交速率、排队数、并发数、单次计算规模、每日 GPU/LLM 预算、超时、上传与结果大小、存储保留期、下载并发。保留现有全局上限，在准入层增加用户/空间限制；共享计数与配额预留必须原子，重试/失败/取消要正确结算和释放。

当前 GPU 推理是全局 FIFO；部分业务限流按 IP 且保存在单进程内。共享办公出口不能代替用户身份，多实例也不能只用各进程计数。先限制单用户活跃/排队数量，业务确需时再增加空间轮转或权重调度。无需把每个用户都拆成独立模型加载进程，也无需为登录立即引入全套分布式任务平台。

文件方面，MD 轨迹、DFT 单文件、bundle 和产物删除应统一继承父任务权限。授权应先于下载槽分配、Worker 请求和文件准备；保留已有路径、hash、断连和临时文件清理检查。私有响应明确 Cache-Control，ETag/304 也先鉴权。新增文件存储时由服务端生成对象名，存储不公开，下载经授权代理或受控短期链接；链接有效期内的转发能力须纳入共享政策。

当前识图上传与部分助手图片在请求内存中处理，不能假设已有用户文件库。只有确需保存历史图像、附件和报告时才引入持久文件实体，并同步做大小/类型限制、生命周期和空间容量。

## 9. 前端状态、缓存及用户体验

需要增加登录与会话恢复、退出、账号设置、权限不足、邀请/成员管理、管理员页面、个人/团队空间选择、“我的任务”与资源归属提示。菜单和按钮由权限驱动，但后端仍是最终授权边界。

API 接入要覆盖 JSON、multipart、SSE、DFT 专用请求、直接 DELETE、轨迹和下载路径，统一处理 401/403、CSRF、请求取消和当前空间。不能只改通用 postJSON，忽略 [api.ts](../frontend/src/services/api.ts) 的专用路径和 [tgAssistantStream.ts](../frontend/src/services/tgAssistantStream.ts)。

重点浏览器存储与状态清单：

| 对象 | 当前情况 | 改造要求 |
|---|---|---|
| 助手会话、页面上下文同意 | 固定 sessionStorage/localStorage 键 | 按用户/空间保存；同意不能跨账号继承 |
| 助手图片 | 固定 IndexedDB，sessionId + messageId，保留 7 天 | 增加身份维度与删除策略，清除 object URL |
| MD、单体 MD、单体聚合草稿 | 固定存储键，含 SMILES/配置 | 作用域化，身份恢复前不加载 |
| 实验流程与 PDF Demo | 本地存真实输入或文件名 | 明确示例/私人数据，旧匿名内容单独处理 |
| 筛选选项和直方图 | 模块级 memoryCache/inFlight；缓存缺身份 | 公共资料可共享版本化缓存；私有结果必须按权限作用域缓存 |
| App 常驻模块、画板、知识标签 | hidden 但仍挂载 | 换账号/空间时清空或重新挂载 |
| OpenScience iframe 与快照 | 全局 URL，生命周期不绑定用户 | 撤销对应会话、重建桥接、丢弃旧消息 |

退出或切换空间的完整流程是：取消待执行请求/SSE/轮询 → 提升会话/空间代次 → 丢弃旧代次回包 → 清状态/缓存/预览 → 切换验证后的新上下文 → 加载新数据。多标签页通过明确的退出同步机制传播状态变化，旧标签恢复时重新确认会话。

本地存储键可包含环境、用户、空间和数据版本；这只是防止应用串号，不是对能检查同一浏览器数据的人提供强保密。敏感持久化应尽量移到已鉴权的服务端，共用设备退出时清理本地科研内容。

不应把所有缓存都机械改成每用户一份：公开模型权重、经授权共享的只读底库、纯公开字典可以继续共享。私人实验统计、候选结果、搜索条件与并发请求复用必须带作用域；权限收回后应失效，不能因命中缓存而跳过鉴权。

## 10. OpenScience / Agent 的独立边界

本仓库能确认的是 iframe 和消息协议，不能确认 OpenScience 服务端已具备多用户。现有消息桥接校验 origin 和 iframe source，应继续保留；但这只验证消息来源，不验证项目/会话所有权。其 overlay 文档还显示当前部署集成依赖已有二进制，需先定位可维护源码或正式身份接口，见 [overlay README](../ops/openscience-ui-overlay/README.md)。

如果第一期向用户提供 Agent，以下内容同样是上线范围：

- 采用同一身份提供方或后端受控会话映射，独立服务也校验用户和空间；直接访问 Agent 地址不能绕过验证。
- 项目列表、会话、文件读写、项目归档和会话删除均由服务端按资源归属授权，不能相信客户端 directory 或当前列表。
- Agent 调用 NexPoly 工具时使用受限、可撤销的委托权限，只能操作获授权资源；提示词中的“当前用户/空间”不能作为授权来源。
- 将可访问目录、工具、凭证、出站网络与执行身份绑定到空间；处理路径穿越和符号链接。共享宿主机 UID、共享可写目录或共享高权限服务密钥不构成强隔离。
- 退出和成员撤销联动会话、长连接、iframe 与快照；浏览器第三方 Cookie 限制、跨源嵌入和 SSO 回调需要实际验证。

具备命令执行的 Agent 建议使用独立受控执行环境和最小挂载，不把整个宿主机或生产运行目录交给普通用户。优先维持清晰的独立服务/来源边界，不能为了 Cookie 方便就默认将高权限 Agent 与主应用放到同一来源。

若短期不能完成上述能力，第一期账号系统可覆盖科研工作台，但 Agent 应继续仅供明确授权的运维人员使用，并对其直接入口执行限制；单纯隐藏 iframe 不足以缩小开放范围。

## 11. 供应商密钥、审计与环境

平台统一模型凭证、用户自带凭证、空间自带凭证是三种不同模式。第一版优先只允许服务端配置供应商；使用平台密钥时 endpoint、model 和出站目标一起由服务端策略确定，不能只隐藏 key 字段。

若允许自带供应商，增加明确权限与凭证保管、脱敏、轮换和删除；地址需校验协议/允许目标，限制内网、loopback、云元数据和重定向等出站路径，同时保留经管理员批准的内部模型服务。相关控制可参照 [OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

日志按用户/空间/资源/动作记录登录、成员变更、权限修改、任务提交/取消/删除、导出/下载和运维操作。安全审计访问本身也需权限；不记录密码、令牌、供应商 key、完整对话或完整未公开配方。保留期、账号离职后的数据移交、删除、备份恢复后的撤权状态需要明确。

当前 nginx 文件监听 HTTP，实际是否存在外部 TLS 终止本次未验证。上线应确定 HTTPS 入口、受信任代理、转发头规则、CORS、Cookie 和回调地址；数据库和 Worker 保持私有访问。现有 [IP 白名单文档](public-ingress-security.md) 明确网络白名单不能替代认证授权。

开发、生产、Agent 当前可能使用同一主机的不同端口。Cookie 不按端口隔离，因此端口分开不能直接沿用为登录安全边界。建议使用独立主机名和 host-only Cookie，并隔离会话库、密钥、身份提供方客户端、回调、凭证和文件根目录。仅更换 Cookie 名称能防止误覆盖，不能阻止同主机另一端口服务接收 Cookie。依据：[RFC 6265 §8.5](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5)。

内部运维现有部分接口已有 loopback/capability 约束，默认 nginx 也只代理 /api 与 /health。应保留这些边界，不能把所有内部接口表述为已经公网暴露。GPU Broker/MPS 属于按环境配置启用的能力，也不能凭代码存在推断当前生产启用。

## 12. 历史数据迁移与现有发布治理

当前历史记录没有可信身份，不能根据 operator 字符串、浏览器 sessionId 或第一次登录账号自动认领。建议逐表统计来源、数量、活跃作业、关联文件和可确认归属，建立迁移映射。无法确认的记录放管理员受限的历史归档空间，普通用户默认看不到。

迁移顺序建议为：

1. 固定归属政策、盘点数据与备份恢复验证，确定必要的写入冻结/排空窗口。
2. 追加兼容迁移，创建身份/空间实体和暂时可空的业务归属列；旧历史仍保持受限。
3. 部署能够对新写入赋予可信归属的代码；迁移期间所有相关写路径必须被同步控制，避免继续产生无主记录。
4. 按经确认的映射回填旧记录和文件归属；保留原业务字段和关联完整性。
5. 修改唯一约束、外键与索引，验证后收紧 NOT NULL/访问策略；兼容性按实际迁移政策判断。
6. 启用最终隔离与验收，保留审计证据。回滚必须仍保持访问边界，不能退回匿名全局 API 后重新开放入口。

本仓库有两项特别重要的工程约束：

- PostgreSQL migrations 是 append-only、checksum 绑定的合约；不能直接修改已应用的 0001/0004/0013 等文件。新增迁移要同步 manifest、migration policy、preflight 与测试。
- DFT 对整个 schema 的列、索引、ACL 和 RLS policy 等做严格指纹校验，新增归属列或权限策略会改变该指纹。必须设计新的合法 schema 版本与迁移兼容检查，不能只加 ALTER TABLE，也不能把旧指纹随意替换成“接受任何结构”。证据：[monomer_dft_schema.py](../backend/app/services/monomer_dft_schema.py)。

现有 [业务数据边界](production-database-data-boundaries.md) 要求正常发布期间在线历史、实验和计算数据保持不变。身份归属回填会真实改变业务行，需独立转换合约及维护流程；新增用户、会话、配额、审计表也必须纳入部署分类、备份和状态变化规则，不能照搬旧的全表摘要假设。包括会话续期、审计和使用量等预期写入，要明确在排空窗口如何处理。

这些工作应先在隔离数据库中完成迁移演练，不需要为本次分析启动、停止或探测生产服务。

## 13. 建议实施包与先后关系

| 工作包 | 必须交付的结果 | 依赖与完成标准 |
|---|---|---|
| A. 范围与数据分类 | 个人/团队规则、角色矩阵、全部 API/数据/文件分类、Agent 首发范围、旧数据归属方案 | 后续工作的共同输入；未归类接口/表不能默认开放 |
| B. 身份基础 | 用户、会话、邀请/重置或 SSO、管理页面、统一认证与错误处理、HTTPS/CSRF | 普通用户能登录；退出/禁用/成员撤销按规则生效 |
| C. 业务资源隔离 | 知识、实验、MD/DFT、内存任务的归属、所有读写及下载授权、约束/索引和 RLS 方案 | A/B 用户无法跨范围读取或更改，全部动作都有覆盖 |
| D. 浏览器隔离 | scoped 存储/缓存、常驻组件清理、多标签同步、旧回包隔离、iframe 生命周期 | 同浏览器换账号与切空间不残留前一范围的数据 |
| E. 计算与运维控制 | 用户/空间配额、服务身份、管理员操作权限、供应商目标绑定、审计 | 单人不能无上限占满队列；普通成员不能触发全局管理动作 |
| F. 迁移与上线门禁 | 新迁移、DFT schema 兼容、旧数据归档/回填、部署分类、恢复和回滚演练 | 验收通过后才开放多人访问；回滚仍保持隔离 |
| G. 后续增强 | 团队/项目细分共享、任务持久化扩展、多副本、公平调度、复杂组织或独立部署 | 按承诺能力和实际规模启用；如首发承诺重启恢复，则任务持久化前置 |

B、C、D 在 A 的契约明确后可以并行，E 与 F 随实现推进。第一版对外提供的每项功能都必须完成相关隔离；不能把 C/D/E/F 当作“以后补安全”。如果 Agent 首发向普通用户开放，第 10 节同样在首版关键路径。

## 14. 验收标准

测试应使用两个用户、两个工作空间，再加同空间不同角色；除了预期拒绝，也要证明合法共享仍能工作。

| 场景 | 预期 |
|---|---|
| 匿名直接请求业务 API、隐藏实验页面对应接口 | 无法读取业务数据、创建或修改资源 |
| B 替换 A 的 history/job/artifact ID | 不能看详情、轨迹、bundle，也不能取消、删产物、删任务 |
| A 清空在线历史 | 只影响其授权范围，B 的历史不变 |
| 两空间用相同样品编号、相同幂等键 | 不互相冲突/复用；同一作用域合法重试保持幂等 |
| 伪造 workspace_id/created_by、跨空间关联子表 | 拒绝；归属由服务端固定 |
| 列表、总数、统计、筛选、导出、缓存命中和 304 | 只反映调用者可见数据，不能通过聚合推断私有记录 |
| A 退出后 B 在同标签登录；多标签切换；请求/SSE 尚未结束时切空间 | 不恢复或闪现 A 的对话、图片、草稿、结构和任务 |
| 禁用用户、移除成员、修改权限 | 原 Cookie 和旧深链接不能继续读取；长连接按撤权策略停止 |
| Worker 回写、重试、后台清理、后台任务重启 | 保持原归属，无任意空间回退；失联任务有明确状态 |
| 并发提交、重试、取消、多实例计数 | 不突破用户/空间额度；不会重复扣费或遗留无限预留 |
| OpenScience 直接入口、项目目录/会话 ID、工具文件访问 | 独立服务验证权限；不能经 Agent 读取其他空间或宿主机管理数据 |
| 普通成员访问 GPU 恢复、全局快照刷新、供应商配置 | 拒绝；获授权管理操作有审计 |
| 平台默认 key 配合客户端自定义 endpoint | 拒绝或强制绑定已批准的服务端 provider；不向未批准目标发送 key |
| RLS 普通运行角色、连接复用和缺失上下文 | 跨范围不可见/不可写；未设置身份不会回退成全库访问 |
| 数据迁移、真实恢复、DFT readiness、回滚 | 原业务内容完整、归属可解释，权限和发布门禁均有效 |

后端使用真实隔离 PostgreSQL，并以实际 API 最小权限角色执行授权测试；创建测试库的管理员连接不能代替普通用户访问路径。前端补覆盖账户切换、异步回包和存储生命周期的行为测试，保持现有单元测试与 TypeScript/Vite 构建门禁。此次仅增加分析文档，未运行会修改测试数据库的测试套件。

## 15. 进入实现前应确定的产品决策

| 决策 | 本文建议默认值 |
|---|---|
| 使用对象 | 先内部研发人员；不立即开放匿名注册 |
| 登录方式 | 已有企业身份则 SSO，否则邀请制本地账号 |
| 默认隔离单元 | 每人个人空间，团队空间显式加入 |
| 私有内容与管理员权限 | 默认私人；管理账号不隐式获得全部科研数据读取权 |
| 科学底库是否共享 | 经分类确认后，平台成员按权限共享只读 |
| 历史数据 | 可确认的映射迁移，其余进入受限归档空间 |
| 用户退出后的作业 | 默认继续；账号禁用/成员撤销另定队列和接管政策 |
| 模型密钥 | 第一版采用受控服务端 provider，限制用户自定义地址 |
| Agent 首发范围 | 具备服务端授权与执行隔离才向普通成员开放 |
| 任务历史承诺 | 若要求重启/跨设备恢复，持久化工作必须进入首版 |

主要工作量来自贯穿所有资源访问路径、旧数据迁移、浏览器状态和独立 Agent 集成。认证组件的选型只有在这些边界明确后，才能形成可验收的用户管理系统。
