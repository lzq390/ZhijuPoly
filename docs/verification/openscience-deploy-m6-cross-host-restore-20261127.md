# deploy-m6 双账号跨物理宿主恢复

2026 年 11 月 27 日，A、B 的工作区从部署宿主恢复到运维指定的第二台物理宿主。两人在源站各发送一份不同的原生文本附件。源站冷备后，目的站使用两个新卷分别启动固定的 11 月版工作区。两人在新浏览器会话中用各自的平台身份登录，读回原同名项目、会话、原模型回答、笔记和本次附件。源宿主与恢复宿主分别计算的摘要按户一致。[逐户摘要和网页登录回执](openscience-deploy-m6-cross-host-restore-20261127.json)

## 镜像、配额工具与余量

目的宿主按镜像 ID 准备了 11 月基础镜像、派生工作区、测试服务、PostgreSQL、UI 及登录 API。宿主默认的 Docker 运行工作区、测试服务和数据库。API 的缺失层展开约 8.87 GiB，因此在同一物理宿主的 `/data` 上用独立客机运行该固定 API。客机只通过回环 SSH 转发两个 Unix socket，连接宿主上的候选 PostgreSQL 和网页入口。存储客机使用固定的 Ubuntu 基础镜像，复核两枚配额内核模块和七个 NFS 软件包的散列后，为恢复卷启用 ext4 内核用户配额。[宿主初始条件](openscience-deploy-m6-recovery-host-20261127.md)

| 目标机可用空间 | 镜像导入、启动探针后 | 双账号网页登录后 |
| --- | ---: | ---: |
| 宿主默认 Docker 卷所在盘 | 41.79 GiB | 41.46 GiB |
| 登录 API 客机的 Docker 卷所在盘 | 58.96 GiB | 58.96 GiB |
| 承载工作区映像和 API 客机的宿主 `/data` | 114.03 GiB | 113.99 GiB |

两个 Docker 数值都取自对应固定镜像新建的匿名卷，按普通用户可用块计算。三处均达到 36 GiB。恢复宿主上可用部署账号运行 `/data/lzq/nexpoly-m6-cross-restore-20261127/tools/bin/check-docker-space` 复测三处余量。

## 网页读回与灰度边界

目的站使用新的候选 PostgreSQL 和登录凭据，登记原 A、B 平台 UUID 与工作区 UUID。测试从实际登录页进入工作台，核对运行容器的镜像 ID 和所挂载的新卷。然后通过已登录工作区的原生接口逐户读取项目、会话、历史回答和附件内容。A、B 最初建项目时创建的会话在源端均为零条消息，恢复后也为零。每户另有一段两条消息的原模型对话，以及本次两条消息的附件对话。完整消息序列、原回答、文件部件 ID 和附件内容摘要均与源端一致。各自的文件列表均能找到本人的验收附件，均找不到对方的附件。直接读取对方同名项目下的附件路径返回空内容。直接读取对方的新会话和旧模型会话均返回 HTTP 404。

本轮验收覆盖工作区及其中已保存的对话和附件。平台账号库、工具任务账本和知识服务数据库的整站灾备属于单独范围。两个保留开发环境的注册表摘要和九个保留卷已按原基线复核。拟开放并发容量和各阶段观察期仍待验收。

本轮现场执行了一次完整的冷备和跨宿主导入。重复传输的流式校验、错配清单和缺件由本地回归覆盖。OpenScience Python 217 项、路由 7 项测试通过。
