# M6 AC-22 双候选环境隔离验收

2026 年 11 月 24 日在同一宿主的两个独立开发候选上，用真实 NexPoly 登录页、11 月 OpenScience 工作区和 Chromium 验收。每个账号使用一个浏览器配置，同时打开两侧页面。A 在两侧使用同一个平台用户 UUID，B 也如此。两个账号分别有各自的登录。生产 9011 和 M1 原私有卷均未参与。[逐项实测](openscience-m6-ac22-20261124.json)

| 候选 | 平台及工作区的 HTTPS 入口 | 工作区存储 |
|---|---|---|
| `dev-m1` | `app.m2.test:18760`、`agent.m2.test:18761` | M5 保留的两份源配额测试卷，继续使用原 UID 和每人 2,000,000,000 字节硬限 |
| `dev-m6` | `app.m6.test:18780`、`agent.m6.test:18781` | 新注册表和两份独立的 Docker 命名卷，每户单独挂载 |

两边各自运行登录与签票服务、PostgreSQL、工作区路由和实例管理器。核对了不同的数据库卷、部署标识、路由凭据和 TLS 公钥。浏览器使用两个域名各自的登录 Cookie。工作区共用了镜像内容，各实例实际运行的 UID、工作区 ID、容器和可写数据卷均逐项区分。普通开发入口继续默认使用 `dev-m1`，指定第二候选会使用它自己的数据根和四个回环端口。[候选配置](../../backend/app/auth/openscience_candidates.json) · [启动程序](../../scripts/openscience_m2_dev.py)

## 同名项目和跨环境票据

登录使用网页表单。建项目、写文件和发送消息通过已登录工作区页面的同源接口执行，侧栏和旧标签状态在实际页面观察。四个工作区分别创建了同一名称的项目和 `notebook.txt`，写入四个不同标记。每户建立了带文件附件的项目对话，并通过本地固定模型收到了回复。四个实例全部回收、两个站点重启后，通过网页找回了原会话、回复及附件，笔记内容和会话标识摘要与回收前相同。[浏览器验收程序](../../scripts/ci/verify_openscience_m6_environments.mjs)

每个工作区分别检查另外三个工作区。12 次按其他会话 ID 读详情均为 404。文件列表只出现自己的标记文件，按其他工作区的专有文件名直接读取也无法取得内容。11 月文件接口对不存在的文本文件返回 HTTP 200 和空文本，验收将每次返回与本户一个从未创建的文件逐项比对。同路径的本人笔记同时可读，四份 SHA-256 均不同。[文件和会话核对](openscience-m6-ac22-20261124.json)

A、B 各在两个方向签票。每次先由接收侧本身的已登录父页向其正常兑换入口提交，再把同一张票提交给签发侧。两轮共 8 次异侧兑换均返回工作区拒绝消息，签发侧均接受同一张票。最长一次从申请到本侧成功兑换不超过 9.093 秒，票据有效期为 60 秒。兑换页使用 HTTP 200 传递浏览器消息，判定依据为工作区的授权结果。[票据及有效期记录](openscience-m6-ac22-20261124.json)

## 名单与总开关

每次操作前，所有旧标签均已读到私人侧栏，四条独立的 SSE 连接均已收到首个事件。从发起名单或开关操作开始计时，分别记录旧页请求被拒、服务端结束事件流、旧标签失效和私人侧栏清空。恢复权限后先用旧页面凭据再查一次，随后用新票据恢复原项目。[控制及容器核验](../../scripts/ci/verify_openscience_m6_environments.py)

名单用例只移出 A。留在同侧的 B 及另一侧的 A、B 继续使用原标签读笔记、写入并读回新内容、申请新票，其原事件流均收到了本人新建会话的事件。总开关用例同时撤销本侧 A、B，另一侧两人的同一组操作均成功。各未中断的事件流中均未见其他账号或环境本轮生成的事件标记。

下表为两轮完整验收中，同一场景所有受影响页面的最长时间。共测得 12 次旧会话撤权和 20 次原会话连续可用。失效的事件流重连均返回 401。

| 操作 | 每轮撤销 / 继续使用 | 旧凭据被拒 | 服务端结束 SSE | 旧标签失效 | 私人侧栏清空 |
|---|---|---:|---:|---:|---:|
| `dev-m1` 移出 A | 1 / 3 | 1.770 秒 | 1.772 秒 | 3.342 秒 | 3.364 秒 |
| `dev-m6` 移出 A | 1 / 3 | 1.977 秒 | 1.978 秒 | 5.033 秒 | 5.084 秒 |
| `dev-m1` 关闭总开关 | 2 / 2 | 2.016 秒 | 2.015 秒 | 4.867 秒 | 4.852 秒 |
| `dev-m6` 关闭总开关 | 2 / 2 | 1.675 秒 | 1.673 秒 | 3.663 秒 | 3.685 秒 |

## 范围与复演

收尾时两边总开关及 A、B 名单均已恢复到演练前的启用状态，两个候选站点都已停止。`dev-m1` 的 A、B UID 分别为 `58161656`、`43620582`，`dev-m6` 的分别为 `20050659`、`81721856`。四个实例均已回收，测试卷保留且无容器占用。M1 原私有卷无容器占用，原注册表及五份保留测试盘镜像的摘要与基线一致。[收尾证据](openscience-m6-ac22-20261124.json)

本项验收覆盖工作区登录、票据、项目、对话、文件与事件流。第二候选使用本地模型测试回复和普通私有卷。它的硬配额、科研工具、模型计费和知识服务没有纳入本项验收。正式灰度仍需目标介质、真实告警送达、跨宿主恢复和拟开放档位的容量证据。[灰度放行条件](../openscience-per-user-instances-plan.md)

两套站点和测试数据均已保留。复演时先恢复 M5 的开发存储虚机和专用转发，再使用 Node 22 在两个终端启动候选。第三个终端可用全新输出目录运行验收，或用 `--fixture` 指向上轮的 `browser.json` 重读已知的四份数据。

```bash
  --registry "$HOME/.local/state/nexpoly-m5-native-01/src"

ac22_work=$(mktemp -d "$PWD/.runtime/ac22.XXXXXX")
python3 scripts/ci/verify_openscience_m6_environments.py verify --work "$ac22_work/run"
```
